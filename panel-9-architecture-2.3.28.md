# Panel 9 (formerly Mobile Browser) — Architecture Guide

*Audience: another bot/engineer who must understand, modify, rebuild and re-publish this app. App-store id: `panel-9` (current 2.3.9). The old store id `mobile-browser` (≤1.1.x installs) is kept only as a hidden "bridge" so old installs upgrade to Panel 9 — see §7. Project folder: `/workspace/mobile-browser`.*

## 1. Overview
Panel 9 is an **Electron browser for Windows x64** (portable exe + NSIS installer) with Chrome-style **profiles**, **unlimited Google accounts per profile** (isolated "account containers"), private windows, history, downloads, favourites/bookmarks bar, a built-in home page, a settings page, and the original per-tab **desktop/mobile device emulation** (phone frame, UA/client-hints/touch/viewport spoofing from JSON device profiles). It updates itself from the Oluchi App Store, passes Google's embedded-browser check for sign-in (§9), and runs **Chrome-style extensions** distributed through the same store (§10).

## 2. Tech stack
Electron ^45 (Chromium engine) · plain CommonJS JavaScript (no bundler, no framework, no TypeScript) · UI = static HTML/CSS/JS rendered in `WebContentsView`s · electron-builder ^26 (win `portable` + `nsis`) · tests are plain scripts run under `xvfb-run electron`. Pure-Node modules (`store.js`, `profiles.js`, `updater.js`, `accounts.js` parsing, `migrate.js`) deliberately avoid importing Electron so they are unit-testable.

## 4. Key modules and data flow
* **Window model (`main.js`)** — one `ctx` per window: `{win, profileId, data (ProfileData), tabs[], activeTab, isPrivate, panel…}`. The chrome UI is one `WebContentsView` (`src/ui`), every tab is its own `WebContentsView` (sandboxed, `contextIsolation`, no Node, **no preload for web content**). `layout()` places toolbar/bookmarks bar/tab view; `phoneLayout()` draws the phone frame in mobile mode.
* **UI ⇄ main IPC** — `src/ui/preload.js` exposes `browserAPI.invoke(action,arg)` limited to an `ACTIONS` whitelist → `ipcMain.handle('ui:<name>')` → `handlers[...]`; main pushes `state` snapshots (`pushState`) to the UI. Internal pages use `window.P9.call(method,args)` → `ipcMain.handle('p9:call')` → `api9[method]`, and the main process re-validates the sender URL (must be `panel9://`).
* **`panel9://` protocol** — registered as privileged scheme; `handlePanel9()` serves only whitelisted page names/extensions from `src/pages` with a strict CSP (`script-src 'self'`, no inline script, `connect-src 'none'`). New internal page = add `<name>.html` + `<name>.js`, add name to `PAGE_NAMES`, add API methods in `api9`.
* **Profiles & containers (`store.js`)** — `userData/panel9.json` (list, last profile, launch mode) + `userData/users/<id>/{settings,containers,history,bookmarks,downloads}.json` (`JsonFile` = debounced atomic writes). A **container** is a named/coloured isolated session: Electron partition `persist:p<profileId>-c<containerId>` (`partitionName()`); the first container (`default`) is the profile's main session. Private windows use in-memory partitions wiped on close (`wipeSessions`). Deleting a profile/container queues `pendingDelete` and the partition data is purged at next start (`purgeDeletedData`).
* **Accounts (`accounts.js`)** — detects "signed in" via Google auth cookies and e-mail via `accounts.google.com/ListAccounts` using the container's own session; shown in the Accounts panel. Nothing leaves the container.
* **Tabs** — `createTab(ctx,url,mode,{container})`; popups/OAuth windows are attached to the opener's session (`attachPopup`) so Google sign-in works; `setTabMode()` toggles desktop/mobile per tab.
* **Emulation** — mobile tab = `emulation.js` CDP overrides + `main.js` `session.webRequest.onBeforeSendHeaders` rewriting `User-Agent`, `Accept-Language`, `Sec-CH-UA*` + `inject.js`. Desktop tab = a normal Chrome UA (no "Electron") and everything cleared. Device profiles: JSON, `{chromeMajor}` templated, loaded from bundled `profiles/`, next to the portable exe, and `%APPDATA%\Panel 9\profiles` (later wins by `id`).
* **Downloads** — `onWillDownload` per session, saved to Downloads (or ask), tracked in `downloads.json`, shown in the toolbar/Downloads page.
* **Updater (`updater.js` + `checkForUpdates()` in main.js)** — see §7.
* **Migration (`migrate.js`)** — first run copies settings, custom device profiles, and `Partitions/browser` cookies from `%APPDATA%/Mobile Browser` into profile `1`; guarded by `migrated-from-mobile-browser.json`.
* Startup (`ready` async block): migrate → `ProfileManager` → purge deletions → load device profiles → picker (if several profiles and "ask on startup") or open last profile → `afterStart()` (update check after 4 s, legacy-rename offer after 9 s).

## 6. Publishing to the App Store
Bump `version` in `package.json` → `npm run dist` → publish (through `bash -lc`; the backend runs on the DigitalOcean droplet, `publish.sh` uploads the exe to R2 then pushes metadata there):
```bash
bash -lc '/workspace/appstore/bin/publish.sh panel-9 <version> "/workspace/mobile-browser/release/Panel 9-<version>-portable.exe" "Release notes" \
  --platform windows --source /workspace/mobile-browser --arch /workspace/mobile-browser/ARCHITECTURE.md'
```
**Also publish the same exe under the legacy id** so Mobile Browser ≤1.1.x installs (which poll `mobile-browser`) upgrade: `publish.sh mobile-browser <version> "<same exe>" "<notes>"` (manifest `mobile-browser` is `hidden:true`, `superseded_by:panel-9`, so it is not listed in the store UI but `/latest` + `/download` keep working). Metadata-only refresh of source/architecture for an existing version (no new binary): `publish.sh panel-9 2.1.0 - --source /workspace/mobile-browser --arch /workspace/mobile-browser/ARCHITECTURE.md`.

## 7. Update-check contract
`GET {STORE_API}/api/apps/panel-9/latest?platform=windows&current=<version>` (`STORE_API` from `src/config.js`, default `https://api10.axionswap.com`; was api10.norhartpro.com until 2.3.27). Used fields: `version`, `url`, `sha256`, `size`, `filename`, `notes`, (`update_available`). Flow: `updater.checkForUpdate` (own semver compare) → dialog with notes (Update now / Later / Skip this version) → `downloadAndVerify` follows the **302 to a presigned R2 URL**, streams to `<dir>/<name>.download`, verifies size + **SHA-256**, deletes on mismatch → `applyUpdate`: portable exe ⇒ spawn a temp `.bat` that waits for the process (and electron-builder's portable launcher, via `PORTABLE_EXECUTABLE_FILE/DIR`) to exit, swaps/renames the exe and relaunches; installed (NSIS) ⇒ opens the downloaded installer. A failed download never touches the current exe. `skippedVersion` is stored per profile settings. Legacy installs of "Mobile Browser" call `/api/apps/mobile-browser/latest` and get the Panel 9 exe (`filename` `Panel 9-<v>-portable.exe`); `legacyRenameTarget()` + `offerLegacyRename()` then offers to rename an old-named exe once.
The store API also exposes `/api/apps/panel-9/source` (this project as a zip) and `/architecture` (this file).

## 8. Gotchas
* **Never** load `panel9://` pages or the preload bridge into web content; keep the sender-URL check in `p9:call`.
* CSP for internal pages forbids inline scripts/styles — put JS/CSS in files.
* Partition names are persistent identifiers (`persist:p<id>-c<id>`); renaming breaks users' logins.
* `package.json` `version` drives both the update comparison and the exe name; the store manifest `file` must match the built file; `sha256` is computed by `publish.sh` from the exact file.
* The `mobile-browser` store id must keep receiving each new Panel 9 exe (hidden) or legacy installs stop updating; conversely do not un-hide it or the store lists the app twice.
* Google sign-in from embedded browsers can still be challenged (risk-based, per IP/account); popups must remain in-app child windows sharing the container session. Do not add a second source of truth for the browser identity — everything goes through `src/identity.js`.
* Electron can only load extensions into **persistent** sessions: private windows opened while an extension is enabled use a disposable `persist:p9priv…` partition that is wiped on close (§10). Extension files must not start with `_` (Chromium reserves those names), which is why the host page is `p9host.html`.
* Windows-only behaviours (`.bat` swap, portable env vars) can't be exercised on the Linux box; `test/update-live.js` and `updater-checks.js` cover the logic, the rest needs a Windows check.
* No secrets in the repo: the store admin token and R2 keys are never required to build; don't commit any.

## 9. Google sign-in ("This browser or app may not be secure")
**Cause.** accounts.google.com fingerprints the page, not just the UA. Panel 9 sent a genuine Chrome UA but Electron's renderer has an incomplete `window.chrome` (no `loadTimes`/`csi`/`app`) and its `navigator.userAgentData` brands did not match the `Sec-CH-UA` header, so Google classified it as an embedded app and refused. (Reproduced on the Linux box with a dummy e-mail; bisected: UA alone is not enough, the missing `window.chrome` members plus the brand mismatch trigger the block.)
**Fix.** `src/identity.js` is the single identity (Chrome major from the running Chromium, brands `Not:A-Brand/Chromium/Google Chrome`, Windows platform). `src/identity-preload.js` is registered with `ses.registerPreloadScript({type:'frame'})` on every session (profiles, containers, private, popups): it only runs when the UA is a desktop Chrome UA (never in mobile emulation) and adds `chrome.loadTimes/csi/app` and a consistent `NavigatorUAData` (`brands`, `getHighEntropyValues`, `toJSON`) with native-looking `toString`. `emulation.js` always rewrites `Sec-CH-UA`, `-Mobile`, `-Platform` from the same source. For `accounts.google.com`, **mobile emulation is suspended for the tab** (`suspendEmulationForGoogle`, resumed when the tab leaves Google auth) because Google also rejects iPhone-Safari UAs with desktop engines; the account page is therefore always seen as desktop Chrome, in normal profiles, containers and private windows.
**Verification.** `npm run test:google` loads `accounts.google.com` sign-in with a dummy address in a normal profile, a container, a private window and a mobile-mode tab and asserts the e-mail form is shown and no "not secure" text appears (screenshots in `shots/google-signin-*.png`). It cannot prove the outcome for a real account: Google's risk engine is also IP/account dependent and the test runs from a datacentre IP; Windows was not available on the box (the box reports a Linux `navigator.platform`).

## 10. Extensions
* **Package format.** Unpacked Chrome extensions (MV2/MV3): `manifest.json` at the zip root, content scripts (incl. `"world":"MAIN"`), `chrome.storage`, action popup / options page. Electron's `session.extensions` implements only a subset of Chrome APIs (no `chrome.tabs` UI, no web store), so keep extensions to content scripts + storage + popup.
* **Store.** Extensions are normal store apps with `type: "extension"` and `target: "panel-9"` (backend `/api/apps?type=extension&target=panel-9`, `/api/extensions`); the Panel 9 binary has `type: "app"` (default for older entries). Publish with `publish.sh <id> <ver> <zip> "notes" --type extension --target panel-9 --platform any --source … --arch …`.
* **`ExtensionManager` (`src/extensions.js`).** Registry `userData/extensions/registry.json`, files in `userData/extensions/<id>/app` (id `local-<slug>` for "Load unpacked", which *copies* the folder). Install = `GET latest` → `updater.downloadAndVerify` (size + SHA-256) → `zip.extractZip` into `staging` → manifest version must equal the store version → atomic swap. Auto-update: 6 s after start and every 6 h (`startAutoUpdate`), toggled on the page; failed/corrupt downloads leave the installed version untouched. All operations run through a serial queue.
* **Every session.** `setupSession()` (called for each profile partition, each container partition — including containers created later — and private windows) calls `extMgr.attachSession(ses)` and `loadExtension()`s every enabled extension; tab creation awaits `sesExtReady` so content scripts exist before the first navigation. Electron cannot load extensions into in-memory sessions, so while at least one extension is enabled a new private window uses a disposable `persist:p9priv<tag>` partition (deleted on close and purged at start); a private window opened *before* the first extension was enabled keeps working without extensions and shows a notice on the toolbar button.
* **Shared `chrome.storage`.** Each session has its own extension storage, so a hidden extension page (`p9host.html/js`, injected into every copy) reports `chrome.storage.local` changes through a tagged `console.log`; the main process mirrors them into a per-extension JSON (`_storage/<id>.json`) and writes them into all other sessions. Net effect: a toggle flipped in one profile/container applies live to all open tabs everywhere and is seeded into new sessions.
* **UI.** 🧩 toolbar button (menu: extensions list, "Manage extensions", "Load unpacked…") + one button per enabled extension with a popup. A popup opens in a small `BaseWindow` (380×560, auto-sized to content, Esc closes) using the active tab's session; the page `panel9://extensions` lists Installed / Store with Install, Remove, Enable/Disable, Reload (unpacked), "Check for updates" and an auto-update switch. After enabling/updating, tabs whose URL matches the content-script patterns are reloaded (`reloadMatchingTabs`).
* **Tests.** `test/ext-checks.js` (in `verify.js`): zip + match patterns, fake store (install, sha256 failure, update on/off, wrong target/type), loading into profile/container/new container/private window, popup toggle → live tab update in all sessions, disable/enable/remove, registry persistence, load unpacked + reload.

## 11. More than 10 Google / YouTube accounts in one profile
**Problem.** Google's multi-login ("Use another account") holds at most **10 accounts per cookie jar**. A profile's Main session and each account container is one cookie jar.
**Design (all built into Panel 9, no extension needed).**
* **Automatic overflow** (`main.js` `maybeOverflowAddAccount` on `will-navigate`/`will-redirect`, `lateOverflowCheck` on `did-start-navigation`, `overflowSignIn`): when a tab whose container already shows ≥ `accounts.cap()` (10; env `P9_GOOGLE_CAP` in tests) accounts goes to an "add account" URL (`accounts.isAddAccountUrl`: `/AddSession`, `flowEntry=AddSession`), the navigation is cancelled and the same sign-in opens in a container of the same profile named `Google 2`, `Google 3`… (`accounts.overflowTarget` reuses one with room, otherwise creates the next). A notice explains it. The user never has to think about containers.
* **One unified list** (`accounts.allPeople(ctx)`): every container's `ListAccounts` people (`parsePeople`: name, email, avatar, `index` = Google `authuser`) are cached in container meta (`store.accountMeta.people`, ≤50 per container, https avatars only) and merged.
* **One switcher.** Toolbar 👥 panel → "Switch Google account" card (search, avatar/name/email/container badge, **Switch**; "Add account" button = `accounts.add`), menu item *Switch Google account…* (Ctrl+Shift+K) and an injected row **"All accounts (Panel 9)…"** in YouTube's/Google's own account menu (`pages/preload.js`, top frames of youtube.com/google.com only, trusted clicks only). Switching = `switchTabToAccount`: the current tab moves to the container holding the account (same URL via `?authuser=N` where needed, same slot, pin state kept).
* **Bridge for extensions/pages.** `window.postMessage({type:'panel9:open-account-switcher'})` from a youtube/google page opens the switcher **only while `navigator.userActivation.isActive`** (real user gesture); the preload sets `data-panel9-switcher="1"` on `<html>` so extensions can feature-detect. The page never receives account data back (one-way). `ipcMain.on('p9:switcher')` re-validates sender tab, main frame and host. yt-focus's comments-only *Switch account* can call this to reach accounts beyond 10.
* Test hooks (TEST only): `P9_GOOGLE_HOSTS`, `P9_GOOGLE_BASE`, `P9_ACCOUNTS_URL`, `P9_BRIDGE_HOSTS`. `test/accounts-checks.js` runs a fake Google (`/ListAccounts` from cookies) with 14–24 accounts.
**Untested against real Google:** the real cap error text, the exact ListAccounts shape/YouTube menu markup (selectors are defensive), brand-channel switching (YouTube's own list per account still applies).

## 12. Proxies / locations (VPN-like, per profile)
**Why built in.** Chrome-style extensions cannot do this in Electron: there is no `chrome.proxy` API (nor `webRequest` proxy auth hooks), so per-profile proxies live in the app. It is independent of any VPN app running on the PC (ExpressVPN etc. keep working for "Direct").
**Data.** `userData/proxies.json` (global list): `{id,label,type http|https|socks5,host,port,username,pw (safeStorage ciphertext),country,tz,lastTest}`. When no OS key store exists (e.g. Linux `basic_text`) the password is kept **in memory only** (never written; user re-enters after restart; the page says so). Assignments live in profile settings (`proxyId` '' = Direct, `proxyKill` default **true**, `proxyAlign` default true, `privateProxy` inherit|direct|id) and container items (`proxy` ''=inherit|'direct'|id).
**Resolution** (`main.js resolveProxy(ctx,cid)`): container override > private-window setting (private windows only) > profile proxy > Direct. Private windows read the *base profile's* settings so changes apply live.
**Applying.** Every session is configured when created (`Ctx.sessionFor` → `initSessionProxy`; tabs wait for `sesProxyReady` before the first request, so there is no unproxied first load) and re-applied on any change (`reapplyProxies`: profile, containers, per-window chrome sessions, popups; old connections are closed). Direct = `{mode:'system'}` (unchanged legacy behaviour, respects Windows proxy/VPN). Proxied = `fixed_servers` with `http://|https://|socks5://host:port` — `socks5://` means **the proxy resolves host names (no local DNS)**; HTTP proxies get the host name in CONNECT/absolute-URI. **Kill switch** = rules **without** `,direct://` (dead proxy ⇒ `ERR_PROXY_CONNECTION_FAILED`, never the PC's IP); off = `…,direct://` fallback. A deleted-but-referenced proxy fails closed (dead-end SOCKS rule) and the button shows "!". The window chrome (toolbar favicons) and overlay panels use per-window sessions (`chromeSession`) so they take the profile's route too.
**Proxy login.** HTTP/HTTPS proxies: `app.on('login')` with `authInfo.isProxy` answers from the store with no prompt (entry chosen by tab → container → proxy id when several share host:port; the same request asking again 3× = rejected → give up, notice + red toolbar button; wrong passwords never loop). **SOCKS5 with a login**: Chromium cannot send SOCKS5 user/pass, so `socksbridge.js` runs a no-auth SOCKS5 server on `127.0.0.1:<random>` per proxy that authenticates upstream (host names are passed through unresolved). Credentials are only in memory; nothing logs them.
**Leak protection.** `webContents.setWebRTCIPHandlingPolicy('disable_non_proxied_udp')` on every proxied tab/popup/extension popup (HTTP proxies carry no UDP ⇒ no WebRTC UDP at all — video calls/STUN-based apps may not work through such a profile; that is the price of no leak). Time zone/language alignment (toggle): CDP `Emulation.setTimezoneOverride` + `setLocaleOverride`, a new-document script for `navigator.language(s)` (needs `Page.enable`), and session Accept-Language via `ses.setUserAgent(ua, langs)`; skipped on Google sign-in pages (which stay plain Chrome). Country→tz/locale table in `proxies.js`; the Test result's own time zone wins.
**UI.** `panel9://proxies` (Menu → *Location & proxies…*): effective location of this tab, assignment card (profile / private windows / kill switch / alignment / per-container selects), proxy list (Test, Use for this profile, edit, delete, Test all, "Check this PC's own connection"), add form (+ "Test before adding"), **bulk paste** (`host:port`, `host:port:user:pass`, `user:pass@host:port`, optional `http://|https://|socks5://` prefix; bad lines stay in the box, passwords are never echoed). Toolbar **location button** (country code, green when proxied, red when failed/missing, 🌐 when Direct) follows the active tab's container; click (or Ctrl+Shift+L) = quick switcher (Direct + every proxy, per-account override submenu, kill switch, alignment, Test, Manage…). **Test** (`testProxy`) uses a throw-away session through the proxy (never falls back to direct) against `https://ipwho.is/` (fallback `ipapi.co`), reporting exit IP, country, latency; the result also fills the country.
**Known limits.** The extension store/update checks and the profile picker window use the PC's connection (they are not browsing). `session.fetch`/downloads/popups of a tab's session are proxied. Windows behaviour of safeStorage (DPAPI) and real proxy providers are untested (box has none).
**Tests.** `test/proxy-checks.js` (+ `proxy-servers.js`): real local HTTP(Basic auth, CONNECT) and SOCKS5 (user/pass and none) proxies dialing out from 127.0.0.11/.12/.13, an http+https target reporting the source address, a UDP STUN counter. Verifies parsing/bulk, encrypted/in-memory password storage, Test results, four simultaneous exit routes (2 profiles + 2 containers, one Direct), silent login, https CONNECT, DNS-at-proxy (`ghost.test`), later-created containers, mobile tabs, popups, private overrides, WebRTC baseline-vs-proxied, kill switch on/off/missing/wrong password, tz/language, button/quick switcher, the page and its form/bulk/Test, no secrets in API/disk/logs. Test env: `P9_PROXY_LOOPBACK=1` (route 127.0.0.1 through the proxy), `P9_IPGEO_URL`.

## 13. Context menus (right-click everywhere)
**Rule.** Every surface gets a Chrome-like native menu; nothing relies on the default (which on Electron is *no menu at all*). ## 2.3.0 — PIA VPN (extension `panel9-pia` + `src/pia.js`)
Electron has no `chrome.proxy`, so PIA is a *manager of Panel 9 proxy entries*, never a second routing layer.

## 2.3.5: Grok Bot control never steals the OS focus
**Problem.** The user works in one Panel 9 window while another agent controls a tab in a second window; every control command pulled focus to the controlled window (`wc.focus()` before mouse/type/key, `ctx.win.focus()` in `open`/`switch`, `activateTab()` -> `webContents.focus()`, `focusOrOpen`/new windows shown active, popped-out web-app `win.show()`). A desktop only has ONE focused window at a time (OS rule), so the fix is not "focus two windows" but "never touch focus at all": the controlled page must work while its window is in the background.
**Rule (enforced by `test:ctlnofocus`).** No control command calls `BrowserWindow/BaseWindow.focus/show/moveTop/restore` or `webContents.focus()` unless the caller passed an explicit `--focus`. The only focus-capable code left in `src/control.js` is `_raise(ctx)` (explicit `--focus`) and `_focusIfActive(t)` (fallback input path, and only when that window already IS the focused one).
* **Input through the Chrome DevTools Protocol** (`Control._cdp/_viaCdp/_mouse/_insert/_press/_clearField`). `wc.debugger.attach('1.3')` once per webContents (state in a `WeakMap`; re-attached automatically if DevTools, `emulation.js` (mobile -> desktop switch detaches) or anything else detached it; `detach` listener resets the flag). Then `Emulation.setFocusEmulationEnabled({enabled:true})` (the page behaves as focused: `document.hasFocus()`, `:focus`, caret) and `Input.dispatchMouseEvent` (mouseMoved, mousePressed, mouseReleased with `clickCount`/`buttons`: `isTrusted` true - Google sign-in still works), `Input.insertText` (typing), `Input.dispatchKeyEvent` (keys: table `NAMED_KEYS`; modifiers bitmask; `text` for characters and Enter; Ctrl/Cmd+A/C/X/V/Z/Y carry the editing `commands` so select-all works through CDP). Coordinates are CSS pixels (what `elements`/`_locate`/`_clickText` already return), so no more view-pixel scaling on this path.
* **Mobile-emulated tabs** (touch emulation on): a left click is a tap (`Input.dispatchTouchEvent` touchStart/touchEnd; CDP mouse presses are never acked in a touch-emulated page and would hang); right click there uses the fallback. Every CDP send has a 10 s cap.
* **Fallback.** If the debugger cannot attach (another client, `P9_CTL_NO_CDP=1`) or a call fails *before anything was dispatched*, the old `sendInputEvent` / `wc.insertText` path runs, but `wc.focus()` is only called when the window is already the focused window (`_focusIfActive`). After the first dispatched event an error is thrown instead (no double clicks).
* **Painting while in the background.** `_prep(t)`: `wc.setBackgroundThrottling(false)` on every controlled view. While control is enabled at startup (`control.json`), `main.js` also starts Chromium with `--disable-features=CalculateNativeWinOcclusion --disable-backgrounding-occluded-windows` so a window fully covered by the user's window keeps painting (needs a restart after first enabling control). `screenshot` races `capturePage` against 10 s and reports an empty/never-rendered frame (minimized window: use `p9ctl switch --focus`).
* **Tabs inside the window.** `_show()` only makes the tab the visible one INSIDE its own window (`activateTab(ctx, id, {focus:false})`: no `webContents.focus()`, no address-bar focus, no raise) because a hidden view does not paint; `close` uses `closeTab(ctx,id,{focus:false})` (neighbour activation + a replacement tab never focus).
* **open / switch / profile / add-account / webapp open** are no-focus by default and take `--focus` (p9ctl help) to additionally raise + focus the window (the old behaviour, `_raise`: restore, show, focus). `open` creates the tab with `createTab(..., {noFocus:true})` and activates it inside its window; when the profile has no window yet `openWindow(pid, {inactive:true})` creates it hidden and `showInactive()`s it (and does not make it the app's "current" window). `switch` = in-window tab switch. `profile.switch` = `focusOrOpen(pid, {focus:false})`. `add-account` = `addGoogleAccount(ctx, {verify:true, noFocus:true})` + in-window activation. `webapp open` = `wa.open(ctx,id,{toggle:false, inactive:true})`: a popped-out web-app `BaseWindow` is created `show:false` and `showInactive()`d (docked sidebars never take focus).
* **Old Panel 9 (< 2.3.5)** ignores `--focus` (it always raised); nothing else on the wire changed. Token, E2E encryption, replay protection and the activity log are unchanged (no new fields are logged).
* **Preserved from 2.3.3/2.3.4** (untouched): trusted clicks for Google (`_clickText` -> `_mouse`, now CDP), updater PowerShell wrapper + `quitForUpdate`, hardened `add-account`, `--webapp` control (`webapp.exec`), log privacy.
* **Tests.** `npm run test:ctlnofocus` (`test/control-nofocus-checks.js`): a second Panel 9 window for another profile is created by control `open` and then driven (click/double/type --clear/--submit/key/scroll/text/elements/eval/wait/shot, background tab, mobile tab, `close`, `add-account`) while window 1 holds the focus; `BaseWindow.prototype.focus/show/showInactive/moveTop/restore/minimize` are spied per window, `webContents.focus` is spied on every view of the controlled window, and the window's own `focus` events are counted: all stay at zero (only `showInactive` is allowed) and the focused window is unchanged. ## 2.3.4: Grok Bot control of web-app extensions (`webapps`, `webapp open|close`, `--webapp`)
**Web-app extensions (background).** An extension whose manifest has a `panel9_webapp` block (Telegram, TechiePoolChat, YT Panel) is not a popup page and not a tab: `src/webapps.js` (`WebApps`, instance `wa` in `main.js`) hosts it in its own `WebContentsView` (`i.content`) plus a 36 px header view and a resize grip, in the persistent partition `persist:p9wa-<profile>-<extId>`. One instance per window+extension (`wa.get(ctx,id)`); docked as a right sidebar (only one docked at a time, `show()` hides the previous) or popped out into a ~400x650 `BaseWindow`; closing only hides it (it keeps running, unread count polled every 3 s). Clicking its toolbar icon = `wa.open(ctx,id)` (toggle). Before 2.3.4 the control layer only knew tabs (`_tabs()/_find()`), so these views were unreachable.
**What 2.3.4 adds (`src/control.js`, `src/webapps.js`, `tools/control/p9ctl`).**
* `webapps` (alias `webapp.list`): `WebApps.list(ctx)` = every installed **enabled** web-app extension: `{id, name, created, open, docked, loaded, url, unread}` (+ `profile`, `window`). `open` = visible now, `created` = a view exists (running, maybe hidden), `url` = the live URL when created, else the configured one.
* `webapp.open` {webapp}: `wa.open(ctx,id,{toggle:false})` - creates the view if needed and shows it exactly like the toolbar icon (idempotent, never toggles it closed), then waits up to 15 s for the first load. `webapp.close`: hides it (keeps running).
* `--webapp <id|name>` = args `{webapp}` instead of `{tab}` on **text, html, elements, eval, click, type, key, scroll, wait, screenshot** (`WEBAPP_CMDS`). `Control._find(id, a)` returns `_findWebapp(a)` when `a.webapp` is set: a pseudo tab `{id:'webapp:<ext>', webapp:i, view:i.content, mode:'desktop', containerId:'default'}` so every existing handler (isolated-world JS, `_locate`, trusted `_mouse` via `sendInputEvent`, `insertText`, `key`, `capturePage`) runs unchanged on the extension's `webContents`. `_show()` for a webapp = `wa.show(i)` when hidden (input/screenshot commands need a visible view; read-only commands - text/html/elements/wait/eval/scroll - work on a hidden running view). A web-app that was never started gives `X has not been opened yet: run "p9ctl webapp open <id>"` (page commands never create views behind the user's back).
* **Name matching** (`Control.matchWebapp`, pure, unit-tested): case-insensitive; exact id > exact name > id without `local-` > prefix of name/id > substring. Ambiguity at the best tier is an error that lists the candidates; unknown names list what is installed. The window is the focused allowed one (or `--profile`).
* **Rules.** `--webapp` with `--tab` is refused; with any other command (`go`, `close`, `switch`, `open`, `add-account`, `signin-google`, ...) it is refused instead of silently acting on a tab. Private windows and profiles that are not on the allow list are invisible (`_webappCtxs`). `eval` still needs the user's "script execution" switch; password inputs are still stripped from `html`; the input pause / password-manager block (`lastInputAt`) applies.
* **Wire format / old-build safety.** p9ctl sends `--webapp` page commands wrapped as `webapp.exec {webapp, cmd, args}` (unwrapped at the top of `Control.run`, inner cmd restricted to `WEBAPP_CMDS`). A Panel 9 older than 2.3.4 has no such command and answers `unknown command: webapp.exec` - it would otherwise have ignored an unknown `webapp` argument and run the command on the active TAB. `p9ctl` adds "update Panel 9 to 2.3.4" to that error. `p9ctl run` users can send `webapp.exec` lines too.
* **Security / log.** Same token, E2E AES-GCM and replay protection (nothing changed in the transport). Activity log (`control-log.jsonl`, shown on `panel9://control`) records `{e: <command>, webapp: <extension name>}` and nothing else for these commands - no host, profile, character count, typed text, selector or page content (the 'type' length is dropped too). Error messages only echo the (clipped) extension name asked for.
* **p9ctl.** `p9ctl webapps | webapp open|close NAME|ID | <page cmd> --webapp NAME` (see `p9ctl help`). Example (Telegram): `p9ctl webapp open telegram; p9ctl text --webapp telegram --selector '.chatlist'; p9ctl type "alice" --webapp telegram --selector 'input[type=search]' --clear; p9ctl click --webapp telegram --index 7; p9ctl type "hello" --webapp telegram --selector '.input-message-input' --submit`. Selectors for Telegram Web K must be read from `p9ctl elements --webapp telegram` / `html`; they are Telegram's, not ours, and can change.
* **Tests.** `npm run test:ctlwebapp` (`test/control-webapp-checks.js`): real relay + real p9ctl + fixture "Telegram"/"TechiePoolChat" web-app extensions (chat list, search box, contenteditable composer): name matching (unit), listing, open/idempotent/unknown/ambiguous, text/html/elements/click(isTrusted)/type/--submit/key/scroll/wait/shot/eval(switch), --tab+--webapp and wrong-command refusal, `webapp.exec` raw protocol, close/hidden reads/auto-show, one sidebar at a time, allow list, private windows, wrong token, activity-log privacy. ## 2.3.1: control reliability (page blink, banner flapping, blank view)
* **What went wrong in 2.3.0.** (a) Every `p9ctl <cmd>` was its own relay connection, so Panel 9 saw "Grok Bot attached → command → detached" in ~500 ms and the
  "controlling" banner (which is part of the chrome height) showed/hid and re-laid-out the content view on every command (32 flips for 20 commands in a desktop tab,
  40 in a mobile tab, measured on the real 2.3.0 build). (b) `panel9://control` rebuilt its whole DOM every 4 s and on each status event, and `.wrap` has an entry
  animation (`rise`), so the page re-played that animation each time ("blinks"). (c) With the relay unreachable the client retried every 1.5 s → 30 s with no jitter and
  pushed a status change on every attempt.
* **Fixes.** `src/control.js`: retry schedule `Control.retryDelay` = 2 s·2ⁿ capped at 60 s with ±20 % jitter; state `waiting` (stable) with `attempt`/`retryAt` in the status;
  connection events go through `_notify()` (coalesced 250 ms, only when the visible state really changed). `src/main.js` `syncControlBanners`: the banner shows at once and
  is **sticky for 60 s** after the last attachment (`P9_BANNER_HOLD_MS` overrides, tests only); switching control off hides it immediately. `layout()` ignores a
  degenerate (< 120 px) window rectangle. **View watchdog** (`viewWatchdog`, every 2.5 s): if the active tab's view is detached, hidden, zero-size, off its expected
  rectangle or its renderer crashed, it is restored (`viewProblem` classifies; `watchdogStats` counts). `src/pages/control.js`: render once, then `refresh()` only
  re-renders when a visible/editable value changed (signature) and otherwise patches the status chip text ("Waiting for relay, retrying in Ns") in place; scroll position is kept.
  `p9.css`/`p9.js`: `.wrap`'s entry animation plays once per page load (`body.settled`). The banner icon no longer pulses forever.
* **p9ctl broker** (`tools/control/p9ctl`): the first invocation starts a background broker that owns ONE relay connection; later invocations talk to it over a user-private
  socket (unix socket / Windows named pipe `\\.\pipe\p9ctl-<id>`) after an HMAC proof of the token; it exits after 120 s idle (`P9CTL_BROKER_IDLE_MS`), `P9CTL_NO_BROKER=1`
  disables it, `p9ctl run` always uses one direct connection. Connection errors exit with code 3.
* **Tests.** `test/control-flicker-checks.js` (relay down: no rebuilds, no animation replay, backoff, banner) and `test/control-burst-checks.js` (20 rapid p9ctl commands,
  real relay, shots `shots/control-burst-*.png`, watchdog, broker). The blank view seen on Windows could NOT be reproduced on Linux/xvfb (the flapping could); the

## 2.3.6 — Web-app view guard (blank / stale web-app windows) (`src/viewguard.js`, `src/webapp/state.*`, `src/webapps.js`)
Root causes found for "the web-app window is blank / shows a stale frame" and the fix for each:
1. **Load before bounds** — docked apps called `loadURL` before the layout gave the view its size, so Chromium could start at 0x0 and never produce a first frame. Now `show()` lays out first, then loads.
2. **`did-fail-load` / `render-process-gone` were stored and ignored** — nothing was retried and nothing was shown. Now: retry 3 times with back-off (1.5 s, 4 s, 10 s) behind a "Reconnecting…" card, then an error card with the reason in plain language, the address and **Retry** / **Open in browser** buttons. Renderer crashes restart automatically (but stop after 3 in a minute and show the card). A renderer that is unresponsive for 6 s is force-restarted.
3. **Stale compositor frame** after minimise/restore, hide/show, maximise, fullscreen, focus or a monitor / DPI change — `repaint()` invalidates and nudges the bounds by 1 px (and restores the exact bounds 30 ms later). Triggered on all of those events for docked and popped-out apps, and on `screen` display events.
4. **No paint verification** — after `did-finish-load` the watchdog checks the DOM (text, media, controls, viewport size) and a sampled compositor frame; if blank: repaint -> reload -> recreate the WebContentsView -> error card. Hidden apps are never judged (checked when shown).
5. **White flash / empty rectangle** — views start with the theme's matte background and a skeleton overlay (own view above the content, same bounds) until the page is verified painted.
* Every recovery is recorded in memory (`webapps.guardLog()`) and appended as JSON lines to `userData/webapp-recovery.log` (rotated at 200 KB; app name, kind, short reason — no page content). Counters: `webapps.guardStats()`.
* `P9_GUARD_SCALE` (env, tests only) scales every guard timing. Test: `npm run test:viewguard` (fixture server: healthy, slow, refused connection + recovery, blank-then-fine, always-blank, crash, hang, crash loop, restore/display change, popped-out window, hidden app, diagnostics).

## 2.3.7 — Updater helper must outlive the app (`src/launcher.js`)
**Symptom (real PC, installed 2.3.4 -> 2.3.6):** the update downloaded and verified, the PowerShell wrapper `%TEMP%\p9-update-setup-*.ps1` was spawned three times (three update prompts in a row), but none ran: no `update-setup.log` (not even "wrapper start"), the `.ps1` was never deleted (its `finally` never ran), the old version relaunched and asked again. Running the same `powershell -ExecutionPolicy Bypass -File` by hand worked and all execution policies were Undefined.

**Root cause (most probable; not reproducible on the Linux build box):** the helper was a plain `child_process.spawn(..., {detached:true})` child of the Electron process and the app quit 300 ms later. `detached` only sets `DETACHED_PROCESS | CREATE_NEW_PROCESS_GROUP`; it does **not** break away from a Windows job object. A process launched from Explorer / a launcher / a security product can live inside a job with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`, and every child spawned from it inherits the job, so when the app (and the job) ended the half-started PowerShell (~1 s startup) was killed before its first statement. Nothing ever checked that the helper had started. (A product blocking `powershell.exe` from `%TEMP%` looks identical; `update-launch.log` now tells the cases apart.) The script itself was checked: it parses cleanly and its first statements run under real PowerShell.

**Fix:**
1. `launchHelper()` starts the helper through a process that is not the app's child and not in its job: **(1) WMI** `Win32_Process.Create` (parent = `WmiPrvSE`), **(2) one-shot Task Scheduler task** (`schtasks /Create ... /SC ONCE`, `/Run`, `/Delete`, current user, no admin), **(3) plain detached spawn**.
2. The helper writes a **handshake file as its very first action** (ps1: first statement, before the mutex and the log; bat: first command). The app polls it (200 ms) and **quits only after it appears**. No handshake in 10 s (or the launch request itself fails) -> next method. Failed requests fail fast.
3. All methods failed -> installed copy: **the setup opens visibly** (`shell.openPath`, app stays open, dialog explains); portable copy: the app stays open, the new exe is kept beside the old one and revealed.
4. **Loop guard** (`update-attempt.json` in userData): two silent attempts at the same version without the version changing -> the third goes straight to the visible installer. Cleared on the first start of the target version.
5. Same launcher for the portable swap `.bat`, the legacy rename `.bat`, and the portable -> installed migration (new `buildRelaunchScript`: waits for the portable app's PID, then starts the installed exe, which previously was spawned directly and also hit the single-instance lock held by the still-running portable app). Swap/rename/relaunch `.bat`s take a lock directory so a slow first method plus a fallback cannot run twice; stale locks (> 10 min) are cleared.
6. `.ps1` is written with a UTF-8 BOM (Windows PowerShell 5.1 reads BOM-less files as ANSI and garbles non-ASCII user names); parent-exit wait raised 15 -> 30 s; leftover `p9-update-*.ps1/.bat/.started` older than 1 h are swept at startup.
7. Every attempt is appended to `userData/update-launch.log` (method, handshake received or the exact failure).

## 2.3.21 — YouTube Focus lean page: session-level request filter (`src/ytf-lean.js`, `src/reqchain.js`)
Why: YouTube Focus 1.4.0 "Comments only" is meant to *load* a weightless YouTube. In Chrome the extension does that with a declarativeNetRequest ruleset (`rules-lean.json`) toggled by its service worker; Electron's extension platform has neither, and the page world cannot stop the parser-inserted `<script src=base.js>` tags, so Panel 9 does it in the main process.
* `src/reqchain.js` — **one** `ses.webRequest.onBeforeRequest` listener per session (Electron keeps only the last one registered). `add(ses, name, fn)` / `remove` / `has`; filters run in registration order, `fn(details) === true` cancels, an exception is ignored. `adblock.js` (`_verdict`) and `ytf-lean.js` are filters in it (`main.js` attaches the ad blocker first, then the lean filter, in `Context.sessionFor`).
* `src/ytf-lean.js` — `leanCancel(url, resourceType)` (pure: the block list; `mainFrame` is never cancelled) and `YtfLean` (`on()` = the YouTube Focus extension is enabled and `peek('commentsOnly') === true` — `extMgr.peek` mirrors `chrome.storage.local`, the ids tried are `yt-focus`, `local-yt-focus`, `local-youtube-focus`; `_fromWatch(d)` = the requesting webContents' URL (or, for the service worker which has no webContents, the referrer) is a youtube.com watch URL or `/sw.js`). `stats`, `recent` (last 50 cancelled URLs). Not cancelled, ever: `youtubei/v1/next`, `youtubei/v1/comment/*`, browse, ytcfg/app scripts, fonts/icons, `/signin`, `/getAccountSwitcherEndpoint`, accounts.google.com, other sites, non-watch YouTube pages.
* Service worker: YouTube's `/sw.js` pre-caches the player with its own XHRs and serves base.js from its cache (invisible to webRequest). The filter cancels `/sw.js` and the worker's player requests; `_poll()` (400 ms, in-memory mirror) wipes `serviceworkers` + `cachestorage` of `https://www.youtube.com` in every attached session when the switch goes ON, and `attach` does it for a session attached while ON. ## 2.3.26 - Mobile control (`src/mobile.js`, `tools/mobile/`)
* **Transport**: the phone is one more client of the control relay room (`wss://.../control?room=<hash of token>&role=client`). Messages are sealed `m1.<kid>.<AES-256-GCM base64>` / pairing `p1.<...>` strings the relay forwards untouched (it drops binary frames and caps 40 msg/s, 8 MB: frames are JPEG base64 inside the sealed envelope, about 1.8x the JPEG; the phone queue paces itself to one message per 38 ms and coalesces scroll / hover / view.set). `Control._onMessage` hands `m1.`/`p1.` to `MobileHub`; Grok Bot traffic is unchanged. `Control.active()` subtracts live phones so a phone never lights the "Grok Bot is working" banner (`mobilescope` AsyncLocalStorage also silences `_grokPresence` / `_noteStep` for phone work).
* **Capture** (`mobilecapture.js`): `composite()` captures each visible view with `capturePage` (never focuses), blends them in z-order into one BGRA buffer at a width chosen by the phone, `encode()` crops (reporting the crop as cut) and JPEG-encodes; popup / extension windows ("extras") and menus float above; `PRIVATE_PAGE` views are skipped. `hitTest()` finds the view under a window point. Extension view = a phone-only hidden BaseWindow (`openExtensionPopup(..., {phone:true})`, `show:false`, `setContentSize`, `setZoomFactor`), captured with `capturePage` of its web contents.
* **Input** is addressed as fractions of the picture the PC last sent: `_resolve` -> window px -> the view -> CSS px (divided by page zoom) with no rounding, then the same `_mouse` / `_insert` / `_press` the p9ctl commands use (CDP `Input.dispatch*`, no OS focus). Ops of one device are serialized (order preserved). Edit detection: `EDIT_JS` in an isolated world lists visible fields + the focused one (as window fractions) every 200-450 ms on the relevant surfaces.
* **Security**: pairing code -> PBKDF2-SHA256 (100k, salt = room) -> pairing key; the phone's request carries a fresh device key sealed with it; devices persisted (`mobile.json`, 0600). Unknown / revoked kid gets one unsigned `unpaired` hint (rate limited). Risky ops (`RISKY` table) are two-step and server enforced; `mobilescope.confirmed()` tells the PC dialog layer the owner already confirmed.
* **PWA**: no framework; `app.js` (Link, view model, gesture engine, keyboard proxy `#kin`, sheets), tokens + icons copied from Panel 9 (`sync-assets.js`), stale-while-revalidate service worker for the shell only. Served by the appstore server at `/m/` (`tools/mobile/server-patch/mobile_bp.py`, strict CSP).
